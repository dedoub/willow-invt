# 경영관리 에이전트 설계

2026-09-30 · 대표님 지시 · 대상: 텐소프트웍스(10월부터 경영관리 일체가 김동욱 이사에게 온다)와 윌로우인베스트먼트(1인 법인, 수입은 ETF 자문)

## 한 줄

**일정을 보고 그 일정에 맞춰 일을 하고, 메일·메시지와 지난 기록으로 일정을 고친다.** 결정이 필요한 것만 윌리로 묻는다.

## 대표님이 정한 것

- 일정이 중심이다. 세 고리로 돈다.
  1. 일정 → 수행: 날짜가 다가오면 그 일을 한다.
  2. 메일·메시지 → 일정 갱신: 새 요청은 일정으로, 바뀐 날짜는 고치고, 끝난 일은 닫는다.
  3. 로그 → 반복 업무 추론: 메일이 없어도 지난 기록에서 반복 규칙을 찾아 다음 회차를 깐다.
- 스페이스 대화는 전부 파악해서 계속 정리하며 쌓는다.
- 일정 등록과 완료 처리는 에이전트가 알아서 한다.
- 자율 범위는 **초안까지**. 사람에게 나가는 발송은 모두 윌리 승인 뒤. 같은 레시피가 몇 달 문제없이 돌면 그 레시피만 한 단계 올린다.
- 윌로우인베스트먼트 경영관리도 같은 에이전트가 맡는다.
- 메일은 이미 연결된 두 메일함만 읽는다: 텐소 `dw.kim@tensoftworks.com`, 윌로우 `dw.kim@willowinvt.com`(추가 연결 없음). 윌로우에는 스페이스가 없다(토큰에 챗 권한 없음, 1인 법인).

### 두 회사 사이의 일과 회사 구분

- 1차는 입력 경로: 윌로우 메일함·신한·KB카드 = 윌로우, 텐소 메일·스페이스·우리은행·우리카드 = 텐소.
- 2차는 상대: ETC·아크로스·키움·타임폴리오 = 윌로우, 성대·평택대·NIA·이맥스·장비고 = 텐소. 세무법인 형운은 공통이라 제목의 상호로 가른다. 독립잇다는 계약 단위로 가른다.
- 두 회사 사이 거래(대여금·용역·지분)는 양쪽 행을 짝으로 만든다. 짝이 없으면 "대사 불일치"로 결정함.
- 도메인 규칙: 김동욱 미지급급여는 윌로우만 지급시점 비용, 텐소는 부채 유지. 차입금 상환과 급여를 섞지 않는다. 대표이사 연봉 결의 문서가 생기기 전에는 미지급 잔액을 단정하지 않는다.
- 미결 사안(결정함 첫 항목): 독립잇다 건의 B2B 정산 여부, 텐소 지분 매입 구조, B2B 기본계약 이사회 승인.

대표님이 실제로 판단한 곳은 넷이다. 처음 보는 거래의 성격, 매출 가안(금액·시점), 발송 승인, 공문서 방식.
반복된 실패는 다섯이다. 안 한 일을 했다고 보고, 아는 걸 또 물음, 회사·업무 규칙 혼동, 엉터리 문서, 멈춤.

## 구조

```
                 ┌──────── 일정 원장 (*_mgmt_schedules) ────────┐
                 │ 예정 → 준비 중 → 결정 대기 → 완료 / 빠짐        │
                 └──▲───────────────▲─────────────────┬─────────┘
       ③ 반복 추론 │   ② 메일·스페이스 │                  │ ① 실행
   mgmt_recurring   │   수집 → 기록부   │                  ▼
   _rules           │   (건·결정·할일·  │           레시피 → 초안 → 확인
                    │    자료·일지)     │                  │
                    └───────────────────┴────── 결정함 → 윌리(버튼)
```

### 일정 원장

새 저장소를 만들지 않는다. 대시보드·윌리·MCP가 이미 읽는 `tensw_mgmt_schedules`·`willow_mgmt_schedules` 를 원장으로 쓰고
`source_key` 를 중복 방지 키로 쓴다(재무 동기화가 검증해 둔 규약).

더할 칸(두 테이블 같게):

| 칸 | 뜻 |
|---|---|
| `origin` | manual / sync / email / chat / inferred |
| `recipe` | 실행할 레시피 키(없으면 null → 사람 일) |
| `agent_state` | planned / preparing / awaiting_decision / done / missed |
| `evidence` | jsonb 배열. 완료·변경 근거(메일 id, 스페이스 메시지 이름, cash id, 고지 id) |
| `rule_id` | 반복 규칙에서 나왔으면 그 규칙 |

`is_completed` 는 그대로 두고 `agent_state='done'` 과 같이 움직인다(화면이 이 칸을 본다).
키 규약: `mgmt:<업무>:<YYYY-MM>:<단계>` (정기), `mgmt-chat:<space>/<message>` (대화발), `mgmt-mail:<messageId>` (메일발).

### 반복 규칙 (고리 ③)

`mgmt_recurring_rules`: 회사, 업무 키, 제목, 규칙(월 n일·말일·n영업일 전·분기 25일 등, 휴일 처리), 준비 시작 리드타임,
레시피, 출처(`seed`/`inferred`), 신뢰도, 근거 목록, 사용 여부.

- **씨앗 규칙**: 스킬과 SOP에 이미 적힌 것(급여 22일 요청·25일 지급, 출근부 말일, 회신 5일, 지원금 15일, 원천세·4대보험 10일,
  부가세 1·4·7·10월 25일, 연말정산·법인세·지방소득세 법인분, 등기부 재발급 3개월). 날짜 계산은 `kr_workdays` 로.
- **추론**: 매일 아침 한 번, 지난 6개월 기록에서 같은 상대·같은 성격의 일이 달마다 비슷한 날에 두 번 이상 일어난 것을 찾는다.
  기록은 원장 완료 행, 은행 입출금, 보낸 메일, 스페이스 요청·완료 짝, 윌리 지시.
  예: GS네오텍 사용내역 확인(7~15일), 체육회 월말 보고서(1~3일), 세무법인 급여대장 요청(22일쯤).
  새 규칙은 `inferred` 로 넣고 저녁 요약에 한 줄로 알린다. 대표님이 "빼"라고 하면 끈다.
- **전개**: 규칙마다 앞으로 60일 안의 회차를 원장에 upsert 한다.
- **빠짐 감지**: 기한이 지났는데 완료 근거가 없으면 `missed` 로 바꾸고 결정함에 올린다.

### 수집과 기록부 (고리 ②)

30분마다(평일 08~20시) 새것만 읽는다. 커서는 `mgmt_source_cursors`(소스별 마지막 시각·id).
- 메일: 텐소·윌로우 두 메일함, `after:` 검색. 보낸 메일도 읽는다(완료 신호). 들어온 경로가 곧 회사 1차 판정이다.
- 스페이스: 활성 24곳. `orderBy createTime desc` 로 커서까지(createTime 필터는 쓰지 않는다 — 0건을 잘못 돌려줬다).
  봇 방(VS Code, Todo-*)과 휴면 방은 기록 대상에서 뺀다.

판단은 Codex(`codex exec --ephemeral`, JSON 스키마 출력)가 한다. 메시지 묶음과 열린 건·일정 목록을 주고 이렇게 받는다.

| 층 | 테이블 | 내용 |
|---|---|---|
| 건 | `mgmt_cases` | 사람들이 "그 건"이라 부르는 사안(NIA 과제, 부스 참가, 장비고 운영). 회사, 상대, 단계, 열림/닫힘 |
| 결정 | `mgmt_entries(kind='decision')` | 누가·언제·무엇을 정했나 한 줄 |
| 할 일 | `mgmt_entries(kind='todo')` | 요청자 → 담당, 기한, 완료 신호. 기한이 있으면 원장 일정도 만든다 |
| 자료 | `mgmt_entries(kind='material')` | 계약서·증명서·계산서 첨부. 법인서류함 등록 여부 |
| 일지 | `mgmt_entries(kind='daily')` | 스페이스마다 하루 한 단락. 건에 안 묶이는 대화는 여기서 끝낸다 |

모든 항목에 원문 링크(`space/message`, gmail id)를 붙인다.
**민감정보는 값 없이 사실만 남긴다**(주민번호도: 6/17 보증보험 메일에 평문으로 오갔다)("[계정정보 공유됨: biblo 챗봇 관리자, 7/26]"). 저장 전에 정규식 가림을 한 번 더 거친다.
평문 공유를 발견하면 결정함에 보안 항목으로 올린다.

완료 신호: "처리했습니다·송금했습니다·발급했습니다·반영되었습니다·제출했습니다", 요청 스레드에 우리가 보낸 답장, 은행 출금·입금 대조, 고지 paid.
신호가 요청과 짝지어지면 할 일과 원장 일정을 닫고 `evidence` 에 근거를 적는다.

기록부는 `/tensw` 경영 화면에서 건 목록·결정 이력으로 보이게 한다(2단계).

### 실행 (고리 ①)

매 주기마다 `agent_state in (planned, preparing)` 이고 `schedule_date - 리드타임 <= 오늘` 인 행을 고른다.
`scripts/lib/mgmt-recipes.ts` 가 레시피 키 → 명령·전제조건·완료 확인 방법을 들고 있다.

| 레시피 | 명령 | 완료 확인 |
|---|---|---|
| payroll-request | `tensw-payroll-request.mjs --month` | 세무법인 스레드에 우리가 보낸 메일 |
| payroll-payday | `tensw_payroll_payday.py` … | 급여 이체 cash 행 |
| payslip-send | `tensw-payslip-send.mjs --month` | 보낸 메일 N통 |
| attendance-send | `gangnam-attendance-send.mjs --month` | 인턴별 보낸 메일 |
| subsidy-collect / subsidy-submit | `gangnam-subsidy-build.mjs collect|submit` | 기관 앞 보낸 메일 |
| tax-due | (명령 없음) 고지 확인·납부 안내 | `finance_tax_obligations.status='paid'` |
| etc-invoice | 윌로우 인보이스 초안(`willow_invoices` draft) + 메일 초안 | ETC 회신 또는 USD 입금 |
| bank-forward | 외화인보이스 송부 메일 초안 | `willow_invoices.sent_to_bank_at` |

- 명령은 초안 모드로만 부른다. `--send` 는 결정함에서 승인이 오면 윌리가 부른다.
- 명령 결과가 초안이면 `awaiting_decision`, 사람 일이면 결정함에 "오늘 할 일"로.
- **완료는 확인으로만 닫는다.** 명령이 0으로 끝났다는 것만으로 닫지 않고, 표의 완료 확인을 다시 조회한다.
- 레시피가 없는 일(5~14번)은 1단계에서는 준비 자료 요약과 알림까지만 한다.

### 결정함과 윌리

`mgmt_decisions`: 일정·건 id, 질문, 선택지, 기본 추천, 근거 링크, 상태(open/answered/expired), 답, 답한 시각.
- 윌리가 버튼 메시지로 보낸다(무엇 / 왜 / 선택지). 답은 결정함에 적고, 해당 일정에 이어서 실행한다.
- **판단 기억**: 같은 종류(같은 거래처·같은 거래 성격·같은 레시피 발송)의 과거 답이 있으면 다시 묻지 않고 그 답을 적용한 뒤 요약에 적는다.
  발송 승인은 예외다. 발송은 매번 묻는다(자율 범위 = 초안까지).
- 결정함에 올리는 것: 발송 승인, 금액이 걸린 결정(예산 밖 지출·가격·계약 조건), 대외 제출 범위, 참석자, 처음 보는 거래 성격, 빠짐, 보안.
- 하루 요약 18:30: 한 일(등록·완료·초안), 새 추론 규칙, 열린 결정.
- 기존 `agent_follow_ups` 는 원장 행을 가리키는 알림 큐로만 쓴다. 키워드 매칭 해소는 원장 경로로 바꾼다.

## 자가 발전 (대표님 2026-09-30: "개발 에이전트처럼 자가 발전")

개발 에이전트가 CEO 지적을 규칙·심사 기준으로 쌓듯, 경영관리 에이전트는 **교정·결정·결과**를 먹고 자기 판단 기준·반복 규칙·스킬 목록을 고친다.
사람이 매번 가르치지 않아도, 같은 실수를 두 번 하지 않는 것이 목표다.

### 1. 교훈 장부 (`mgmt_lessons`)

| 들어오는 길 | 예 | 교훈 |
|---|---|---|
| 대표님이 에이전트가 쓴 일정을 되돌림 | 에이전트가 닫은 행을 다시 열기, 지우기, 날짜 옮기기 | "X 근거로 닫았지만 대표가 다시 열었다" |
| 결정함 답 | 같은 종류 판단의 답 | 판단 기억(이미 있음) + 교훈 한 줄 |
| 윌리에게 직접 교정 | "경영관리 교훈: 형운 메일은 제목 상호로 회사 가른다" | 그대로 |
| 규칙 거절 | 추정 규칙에 "빼" | "이 반복은 업무가 아니다" |

- 에이전트가 쓴 행은 `mgmt_agent_writes`(테이블·id·source_key·쓴 값 요약·시각)에 남긴다. 다음 실행에서 그 행이 사람 손으로 바뀌었으면(삭제·재개방·날짜 변경) 교훈 후보로 만든다.
- 활성 교훈은 해석(Codex) 프롬프트 맨 앞에 회사별 최근 20개가 들어간다. 교훈마다 적용 횟수(`hits`)를 센다.
- 교훈에는 원래 입력(가린 문장)과 기대 결과를 예시로 붙인다. 재현 시험이 교훈 예시를 회귀 사례로 돌린다.

### 2. 규칙 스스로 조정

- 매주 규칙마다 최근 3회차의 **예정일 대 실제 완료 근거일**을 본다. 셋 다 2일 넘게 같은 방향으로 어긋나면 날짜를 옮기고(월 n일 규칙) 교훈·요약에 적는다.
- 두 회차 연속 `missed` 인 규칙은 결정함에 "규칙을 끌까요?"로 올린다.
- 추정 규칙이 두 회차 동안 근거가 한 번도 없으면 스스로 끈다.
- 추정 규칙이 세 회차 연속 근거로 닫히면 `confidence` 를 올리고 "추정" 표시를 뗀다.

### 3. 주간 점검과 개선 제안 (월요일 07:30)

- **성적표**: 만든 일정·근거로 닫은 일정·대표가 되돌린 일정·빠짐·물어본 결정·재사용한 판단·해석 실패. 되돌림 비율이 오르면 원인 교훈을 함께 보인다.
- **스킬 후보**: 레시피 없는 같은 종류의 할 일이 4주 안에 3번 넘게 김동욱 이사 앞으로 온 경우, 개발 에이전트 몫으로 넘긴다(`ws_threads` 에 `project='willow-invt'`, 태그 `mgmt-skill-request`, 근거 링크 포함). 개발 에이전트가 스킬을 만들면 레시피 표에 붙는다.
- **자율 단계 제안**(2단계부터): 같은 레시피가 3회 연속 수정 없이 승인되면 "이 레시피는 승인 없이 초안→발송 해도 될까요?"를 결정함에 올린다. 대표 승인 없이는 올리지 않는다.
