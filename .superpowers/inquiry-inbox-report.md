## 2. 브리핑과 라이브가 갈린 곳 — 셋

브리핑의 표를 그대로 믿지 않고 네 DB에 직접 물었다. 세 군데가 달랐고, **셋 다 그대로
갔으면 화면이 틀렸다.**

### 2.1 포틀 `inquiry_threads` 에는 `account_id` 가 없다

브리핑: *"Portle's is similar (it also has app_version, platform, locale)."*
라이브: `account_id` → **42703 column does not exist**.

실제 컬럼은 `id, subject, access_token, channel, created_at, last_message_at,
unread_for_user, unread_for_admin, app_version, platform, locale,
telegram_message_id, draft_body, draft_at, drafted_by`.

포틀의 신원 컬럼은 **`subject`**(`text not null unique`)다. 값은 `google:…` / `device:…`
꼴 — 보이스카드 `account_id` 와 같은 자리를 차지하는 같은 종류의 값이지, 문의 제목이
아니다. 정본은 `port-ledger-backend/supabase/migrations/20260827000000_inquiry.sql`.

→ 앱별 컬럼 대응표를 `INQUIRY_APPS` 로 두고, 포틀만 `person: 'subject'` 로 잡았다.
시험 2건이 이걸 붙잡는다.

### 2.2 리뷰노트 `sender` 는 대문자다 (브리핑이 확인하라고 한 대로)

`InquirySender` enum = **`USER` / `SUPPORT`**. 소문자로 물으면
`22P02 invalid input value for enum "InquirySender": "user"`.
`prisma/schema.prisma:679` 로도 교차 확인했다.

스크립타는 `scripta_inquiry_sender` enum 이지만 값이 소문자(`user`/`support`)다.
보이스카드·포틀은 enum 이 아니라 `text ... check (sender in ('user','support'))` 라
PostgREST 단계에서는 어떤 값이든 통과한다.

→ 모르는 `sender` 값은 **기본값으로 접지 않고 던진다.** 접었다면 고객이 쓴 말이 우리
답변으로(또는 반대로) 보인다. 대화 화면에서 그건 조용한 오답이다.

### 2.3 🔴 리뷰노트 시각에는 시간대가 없다 — 내가 넣을 뻔한 버그

브리핑에 없던 것이고, 처음엔 **나도 놓쳤다.** 뮤테이션 시험에서 살아남은 뮤턴트 하나를
쫓다가 발견했다.

```
리뷰노트   "2025-10-12T15:49:12.129"            ← 오프셋 없음
보이스카드 "2026-06-22T16:00:06.776496+00:00"
포틀       "2026-08-07T03:02:32.160352+00:00"
```

Prisma `DateTime` 은 `@db.Timestamptz` 를 안 붙이면 `timestamp(3)`(시간대 없음)로
떨어진다. 값 자체는 UTC 인데 **JS 는 오프셋 없는 ISO 를 로컬 시각으로 읽는다.**
KST 기기에서 리뷰노트 문의만 아홉 시간 일찍 서고 아홉 시간 이른 시각으로 보였을 것이다 —
방금 온 문의가 목록 한참 아래로 내려간다. 네 앱을 한 줄로 섞어 세우는 화면이라 이게 곧
"미답변 먼저" 를 무너뜨린다.

→ `toInstant()` 로 DTO 단계에서 시간대를 붙인다. 시험은 기기 시간대와 무관하게 실패하도록
썼고(`endsWith('Z')` + `Date.parse` 동치), KST·UTC 양쪽에서 뮤턴트가 죽는 걸 확인했다.

### 그 밖에 확인한 것

- 리뷰노트 `InquiryThread.userId` 는 uuid 가 아니라 **cuid(String)** 이다. 파싱하지
  않으므로 동작에는 영향 없다.
- 리뷰노트·스크립타 스레드에는 `channel` 컬럼이 없다(보이스카드·포틀만 있다).
- **PostgREST 는 식별자를 스스로 인용한다.** `.from('InquiryThread').select('userId,…')`
  가 그대로 동작한다 — 브리핑의 큰따옴표 경고는 **생 SQL** 에만 해당한다. 코드에
  주석으로 남겨 뒀다. (라이브 조회로 확인했다.)

## 3. 판정이 갈린 지점 두 곳

### 3.1 발행: 두 번 쓰지 않고 앱의 RPC 를 부른다 — 브리핑에서 벗어난 유일한 곳

브리핑은 *"insert a message …, then set unread_for_user = true …"* 순서를 지시했고,
*"insert 는 됐는데 flag update 가 실패하면 성공이라고 하지 말 것"* 을 요구했다.

두 앱 모두 이미 **`publish_inquiry_reply(uuid, text, text)`** 를 갖고 있다.
`security definer` 함수 하나가 한 트랜잭션 안에서 삽입 + 세 플래그를 전부 세운다.
보이스카드 마이그레이션 `085_inquiry.sql:65` 주석이 이렇게 못박아 뒀다:

> 발행의 유일한 정문. 텔레그램 답장도 **대시보드도** 이 함수만 부른다 — 쓰는 곳이
> 둘이면 언젠가 한쪽만 고쳐지고, 갈라진 것은 눈으로 찾기 어렵다.

즉 이 대시보드를 **예상하고 쓰인 함수**다(현재 호출자는 어디에도 없다 — 우리가 첫 호출자다).

라이브로 확인한 것:
- 두 프로젝트 모두 3인자 형태가 존재한다(없는 스레드를 주면 `PGRST202` 가 아니라 함수
  본문의 `P0001: no such thread` 가 나온다 — 함수가 실제로 실행됐다는 뜻).
- 우리 service key 로 `execute` 가 열려 있다(`grant execute … to service_role`).

**그래서 지시한 두 단계 대신 이 함수를 부른다.** 지시의 글자에서는 벗어나지만 목적에는
더 충실하다 — "중간에 실패하면 뭐가 남나" 라는 상태가 **아예 존재할 수 없다.** 함수가
던지면 삽입도 함께 되돌아간다. 덤으로 초안(`draft_*`)까지 같은 트랜잭션에서 지운다.

⚠️ 다르게 하고 싶으면 말해 달라. 되돌리는 건 `publishInquiryReply` 한 함수뿐이다.

### 3.2 구버전(`channel='email'`) 스레드에는 쓰기를 막았다

`channel in ('app','email')` 이고, `email` 은 구버전 Apps Script 문의다 — 그쪽 고객에게는
**앱 안 문의함이 없다.** 여기서 발행하면 DB 에는 답이 남고 화면은 성공을 보여주지만 고객은
영영 못 본다. 정확히 "성공처럼 보이는 실패" 라 **409 로 막고**, 목록에는 `구버전` 배지,
대화창에는 답변칸 대신 이유를 띄운다.

RPC 는 커밋한 뒤에야 channel 을 돌려주므로 되돌릴 수 없다 → **부르기 전에** 확인한다.
이메일 발송은 하지 않는다(요청대로, 그리고 `inquiry_legacy_contacts` 를 읽지 않는다).

## 4. 두 가지 실패 모드

### 4.1 실패한 발행이 성공처럼 보이면 안 된다

- 초안은 `Record<threadId, string>`, **실패도** `Record<threadId, string>`. 둘 다
  `composeKey(app, id)` 로 키를 잡는다 — 앱이 다르면 스레드 id 가 겹칠 수 있다.
- 입력창은 **서버가 `{ok:true}` 를 돌려준 뒤에만** 비운다(`publishSucceeded`).
- `publishFailed` 는 초안을 손대지 않는다.

### 4.2 늦게 온 응답이 엉뚱한 스레드에 꽂히면 안 된다

`createLatestOnly()` — 요청마다 번호를 올리고, 응답 시점에 번호가 그대로일 때만 반영한다.
**가드는 한 겹뿐이다.** 컴포넌트에는 `isCurrent` 검사 외에 스레드 id 를 다시 대조하는
곳이 없다(두 겹이면 하나가 죽어도 시험이 초록이라, 죽은 걸 아무도 모른다 — 형제 앱에서
실제로 그렇게 됐다).

핀은 겹치는 두 선택으로 박았다: A 시작 → B 시작 → B 도착(반영) → A 도착(**버림**).

## 5. 시험 — 부순 뒤에 봤다

**39건 신규**(core 28 · compose 11) · 전부 통과.
회귀: `npx tsx --test src/lib/__tests__/*.test.ts` **90/90**, `npm run finance:test`
**163/163**, `npx tsc --noEmit` 무오류, `npm run build` 성공(세 라우트 + `/inquiries`
모두 등록됨), eslint 무오류.

주장이 공허하지 않게 한 장치 하나: 가짜 조회기가 **받은 인자를 전부 기록한다.** "리뷰노트를
대문자 컬럼으로 물었나", "1000행 뒤 다음 구간을 요청했나", "그 스레드로 좁혔나" 는
돌려준 값이 아니라 **호출 인자**로 확인한다. 무엇을 받든 같은 걸 돌려주는 가짜였다면 이
주장들은 전부 무의미했을 것이다.

### 뮤테이션: 21개를 만들어 돌리고 되돌렸다 — 20개 사망

| 부순 구현 | 죽인 시험 |
|---|---|
| DTO 가 행을 `{...row}` 로 펼침 | 토큰도 초안도 따라오지 않는다 |
| 정렬에서 미답변 우선 제거 | 미답변이 먼저 (+1) |
| 페이지를 한 번만 읽음 | 1000행에서 멈추지 않는다 (+1) |
| 상한에서 조용히 자름 | 잘라서 돌려주지 않고 던진다 |
| 조회 실패를 `{status:'ok', threads:[]}` 로 접음 | 빈 목록으로 접지 않는다 (+1) |
| 빈 `role` 을 통과시킴 | role 이 비어 있으면 관리자가 아니다 |
| 세션 없음도 403 으로 묶음 | 401 과 403 은 다른 사실이다 |
| 리뷰노트 `sender` 를 소문자로 봄 | 대문자다 (+1) |
| 리뷰노트를 스네이크 컬럼으로 조회 | Prisma 대소문자 컬럼으로 조회한다 |
| 포틀 신원을 `account_id` 로 봄 | subject 다 (+1) |
| 모르는 `sender` 를 `'user'` 로 접음 | 기본값으로 접지 않고 던진다 |
| 읽기 전용 앱 검사 제거 | 여기서 쓰지 않는다 |
| 이메일 채널 검사 제거 | 써도 고객이 못 본다 |
| 메시지를 스레드로 안 좁힘 | 그 스레드로 좁힌다 |
| 실패해도 초안을 지움 | 쓴 글이 남는다 |
| 실패 표시를 전역으로 | 그 스레드 칸에만 남는다 |
| **`isCurrent` 가 늘 true** (형제 앱 실제 결함) | 늦게 온 응답은 버려진다 (+2) |
| `isCurrent` 가 `ticket <= seq` | 늦게 온 응답은 버려진다 (+2) |
| `toInstant` 를 항등으로 | 오프셋 없는 시각은 UTC 로 읽는다 |
| DTO 에서 `toInstant` 만 제거 | 오프셋 없는 시각은 UTC 로 읽는다 |

### 살아남은 하나 — 정직하게 적는다

**`Date.parse` 를 `localeCompare` 로 바꿔도 아무 시험이 실패하지 않는다.**

처음엔 잡는다고 주장하는 시험이 있었는데, 확인해 보니 **엉뚱한 이유로 통과하고 있었다**
(내가 고른 두 값이 연도부터 달라서 문자열 비교로도 순서가 맞았다). 그래서 그 시험을
버리고, 진짜 결함(2.3 시간대)을 잡는 시험으로 갈아 끼웠다.

`toInstant` 로 정규화한 뒤에는 네 앱의 시각이 `…Z` 와 `…+00:00` 두 모양뿐이고, 실제로
오는 값(초 아래 자릿수가 항상 붙는다)에서는 문자열 비교와 시각 비교가 **언제나 같은
순서**를 낸다. 실패시킬 수 있는 입력을 만들려면 이 네 DB 가 내놓지 않는 값을 지어내야
한다 — 그런 시험은 허구를 지키는 시험이라 쓰지 않았다.

`Date.parse` 를 그대로 둔 건 시험이 강제해서가 아니라 그게 맞아서다. **이 한 줄은
시험이 지키지 않는다.**

## 6. 그 밖에 지킨 것

- **`access_token` · `draft_*` 는 조회조차 하지 않는다.** DTO 는 행을 펼치지 않고 한 칸씩
  옮겨 적는다. 시험이 키 목록을 정확히 대조하고, **값**도 확인한다(키 이름만 보면 다른
  칸에 담아 내보내도 통과하므로).
- **상한 없음.** PostgREST 1000행 절단은 페이지로 이어 읽어 넘긴다. 폭주 방지 상한
  (500페이지)에 닿으면 **잘라서 돌려주지 않고 던진다.**
- **깨진 조회는 절대 0건으로 안 그린다.** 앱별로 `{status:'error', message}` 가 나가고
  화면에 빨간 줄로 뜬다. 네 앱이 다 성공하고 문의만 없을 때에만 "문의는 아직 없다" 가
  나온다 — 이 두 화면이 지금 눈으로 구별된다.
- **401 ≠ 403.** `adminGate()` 한 곳에서 판정하고 목록·대화·발행 세 라우트와 페이지가
  같은 판정을 쓴다. **빈 role 은 관리자가 아니다.** 페이지는 클라이언트 `useIsAdmin()`
  이 아니라 **서버 컴포넌트에서** `getAuthUser()` 로 잠근다(세션 없음 → `/login`,
  관리자 아님 → `/`).
- **이메일·계정 식별자 추가 조회 없음.** `auth.users` 조인 없음. 화면에 뜨는 신원값은
  스키마가 이미 들고 있는 `account_id` / `subject` / `user_id` / `userId` 앞 18자뿐이다.
- **정렬**: 미답변 먼저, 그 안에서 최근 순. 네 앱을 섞어 한 줄로 세운다.
- **스키마 무변경.** 조회는 전부 읽기 전용, 쓰기는 기존 RPC 호출뿐.
- **UI** 는 `linear-tokens` + `LCard`/`LSectionHead`/`LBadge`/`LBtn`/`LHeadBtn` 로,
  `scripta/page.tsx` 껍데기를 따랐다. 한국어.

## 7. 마음에 걸리는 것

1. **네 앱 전부 문의가 0건이다.** 그래서 화면을 **실제 데이터로 본 적이 없다.** 읽기
   경로는 라이브 네 DB에 붙여 컬럼 하나까지 확인했지만(2.x 의 세 발견이 그 산물이다),
   "메시지가 실제로 그려지는 모습" 은 확인 못 했다. 첫 문의가 들어오면 한 번 눈으로
   볼 것을 권한다.
2. **발행은 한 번도 실행해 보지 않았다.** RPC 가 존재하고 우리 키로 호출 가능하다는
   것까지만 확인했다(없는 스레드로 찔러 함수 본문 예외를 받았다). 진짜 발행은 고객에게
   메시지를 보내는 일이라 임의로 하지 않았다. 첫 답변은 지켜보면서 보내면 좋겠다.
3. **`main` 이 남의 변경으로 dirty 했다**(SEO 색인 · 재무 · supabase SQL · vercel.json).
   문의함과 겹치는 파일은 하나도 없다. 내 파일만 경로로 지정해 커밋했고 남의 변경은
   건드리지 않았다.
4. **§3.1 의 RPC 판단**이 지시한 두 단계에서 벗어난 곳이다. 근거는 적어 뒀지만 판단은
   판단이다.
5. `linear-sidebar.tsx` 에 이미 있던 `react-hooks/set-state-in-effect` 린트 오류
   (171행, `useOrderedGroup`)는 **내 변경 전부터 있던 것**이다(HEAD 에서 확인). 손대지
   않았다.
6. 목록 라우트가 네 앱 스레드를 **전량** 실어 보낸다(상한이 없어야 하므로). 지금은 0건이라
   문제가 없지만 수천 건이 쌓이면 첫 페이로드가 무거워진다. 그때는 목록에 커서를 넣는 게
   맞고, 그건 "상한" 과 다른 이야기다.
